# Delhivery Last-Mile Delay Intelligence Pipeline

**Applied AI/ML capstone · E&ICT Academy, IIT Roorkee**

This repository implements one connected, reproducible offline pipeline for synthetic last-mile shipment data: data quality and delay evidence, delivery-hours regression, delayed-parcel classification, hub segmentation, model packaging, and a batch action list for 48 new parcels.

> **Data note:** all shipment records are generated by the supplied `generate_data.py`. This is a synthetic case study. It does not use Delhivery's private records and is not evidence of a deployed Delhivery system.

## How to run

Run the following commands from the repository root, in this exact order, after cloning the repository. The provided generator must be committed unchanged; it regenerates the three source CSVs.

```bash
git clone https://github.com/<your-username>/delhivery-delay-intelligence.git
cd delhivery-delay-intelligence
python -m pip install -r requirements.txt
python generate_data.py
python part_a_clean_eda.py
python part_b_regression.py
python part_c_classification.py
python part_d_segments.py
python package_model.py
python predict_delay.py
```

`generate_data.py` prints `24 1224 48`. The scripts create the modelling table, model-comparison tables, hub segments, model artifacts, reload check, and final 48-row action list under `data/`, `outputs/`, and `models/`. All CSVs are written without a pandas index unless an index is the intended first column of the correlation matrix.

`models/delay_model.pkl` is regenerated by running `python package_model.py`. A pickle must be loaded with the compatible scikit-learn version that created it; this repository pins the exact package versions in `requirements.txt`. The grader can regenerate the artifact with `package_model.py` if its installed versions differ. The current pinned versions used to generate the committed artifacts are pandas 2.2.3, NumPy 2.3.5, scikit-learn 1.8.0, and joblib 1.5.3.

## Data findings

The observations below are calculated from `outputs/part_a_checks.csv`, `outputs/part_a_delay_by_group.csv`, and `outputs/part_a_correlations.csv`.

1. **Service type:** Express has the highest observed delay rate: **119 of 243 parcels, or 0.4897 (48.97%)**. Standard is 0.2056 and Economy is 0.0857.
2. **Hub tier:** delay rate rises from **0.0400 (4.00%) for Tier 1** to **0.2150 (21.50%) for Tier 2** and **0.4400 (44.00%) for Tier 3**. This supports reviewing hub operating conditions rather than treating tier as a guarantee of performance.
3. **Distance band:** the observed delay rate rises with distance: **0.0219** for 0–200 km, **0.1368** for 201–400 km, **0.4364** for 401–600 km, and **0.8523** for 601+ km.
4. **Correlations with delivery hours:** the three largest absolute correlations, excluding `delivery_hours` itself, are `promised_hours` (**+0.8372**), `distance_km` (**+0.4013**), and `n_stops` (**+0.3247**). Correlation indicates association, not causation.
5. **Declared value transformation:** after median filling, `declared_value_inr` has mean **INR 1,533.0542** and median **INR 1,121.5000**; its natural-log transform has mean **7.0277** and median **7.0224**. The transformed mean and median are much closer, consistent with compressing the high-value tail and reducing scale skew.

The raw file has **1,224 rows**; the cleaning step removes **24 exact duplicates**, leaving **1,200 unique shipment rows**. There are **278 delayed parcels**, a delay rate of **0.2317**, and **zero missing cells** across the 17 model features and the two targets in the modelling table. The three fill medians are distance **314.9500 km**, parcel weight **1.8300 kg**, and declared value **INR 1,121.5000**. Five parcel-weight values above 100 kg are handled as scanner-fault sentinels.

## Model results (regression)

The regression uses the 17 features in the pinned order and splits rows into 840 training, 180 validation, and 180 test records using the specified random seed. The `StandardScaler` check in `outputs/part_b_checks.csv` has a training maximum absolute column mean of **0.0000** (below `1e-9`) and a test maximum absolute column mean of **0.2187**, evidence that the scaler was not fitted on the test records.

- **Baseline:** the training-target-mean baseline obtains validation R² **-0.0212**. It is worse than simply predicting the validation mean because it does not explain the row-to-row variation in delivery duration.
- **Validation winner:** `linear_regression` has validation RMSE **4.8912 hours** and R² **0.9313**. Gradient boosting is close at RMSE **4.9165 hours** and R² **0.9306**. Linear regression is selected as the final Part B candidate because it has the lower validation RMSE under the required decision rule.
- **Tree-depth diagnosis:** depth 1 has train RMSE **11.6334** and validation RMSE **12.1324**, consistent with high bias. The unrestricted tree has train RMSE **0.0000** but validation RMSE **7.8368**, a large generalisation gap consistent with high variance. Depth **6** is the best diagnostic depth with validation RMSE **6.2796**.
- **Learning-rate experiment:** gradient boosting at learning rate **0.1** performs best, with R² **0.9306**. At **0.01**, R² is **0.7127**: 100 boosting stages learn too slowly. At **1.0**, R² falls to **0.8440**, consistent with overly aggressive updates and a less stable fit.
- **Cross-validation:** on the combined 1,020 training-plus-validation records, the two strongest validation candidates achieve mean R² **0.9261** for linear regression and **0.9353** for gradient boosting, with standard deviations **0.0048** and **0.0045** respectively. Cross-validation slightly favours gradient boosting, but the prescribed final selection is by validation RMSE, which narrowly favours linear regression. The gap is small; in a larger production evaluation, this decision should be confirmed on repeated temporal or grouped splits.
- **Single test evaluation of the selected model:** linear regression records test RMSE **4.5235 hours** and R² **0.9493**. No model comparison or tuning decision was made using this test score.

## Model results (classification)

The classification split is stratified, with **195 / 42 / 41** delayed shipments in training, validation, and test sets. The blind “all on time” baseline reaches accuracy **0.7667** but recall and F1 are both **0.0000**: it catches none of the delayed parcels, so accuracy alone is not a useful operational objective.

- **Validation models:** logistic regression reaches F1 **0.8046**; the best decision tree is depth **6** with F1 **0.7470**; the default random forest on all features reaches F1 **0.7848**.
- **Feature signal:** the top seven univariate F-score features are, in rank order, `distance_km`, `hub_tier`, `hub_daily_capacity`, `n_stops`, `promised_hours`, `rain_flag`, and `sale_event_flag`. The five bookkeeping/noise columns contribute a combined **0.2245** (22.45%) of the all-feature random-forest importance. All five fall outside the top seven F-score ranks, and each has an F-score below 10.
- **Number of selected features:** in `outputs/part_c_selectk.csv`, **k = 7** is best on validation with F1 **0.8333**. The validation F1 is lower for k = 5 (**0.6988**), k = 10 (**0.7857**), k = 12 (**0.8049**), and k = 17 (**0.7848**), supporting the seven-feature choice for this split.
- **Tuning:** grid search, randomized search, and the untuned forest on the same seven features produce validation F1 values **0.7750**, **0.7848**, and **0.8333** respectively. Tuning therefore does not beat the untuned version on this validation split. The grid has 27 candidates / 135 fits and the randomized search has 9 candidates / 45 fits; their CV accuracy objectives do not directly optimize F1, and a validation set of 180 records makes small ranking differences uncertain.
- **Alert threshold:** the operations rule is to use the highest threshold with validation recall at least 0.80. The selected threshold is **0.5**, where validation precision is **0.7955** and recall is **0.8333**. Raising it to 0.6 reduces recall to 0.7619, below the required floor.
- **Final test result:** at threshold **0.5**, precision is **0.6889**, recall **0.7561**, and F1 **0.7209**. In practical terms, about **6.9 of every 10 flagged parcels** are delayed, and about **7.6 of every 10 delayed parcels** are caught. Test recall is lower than validation recall (0.7561 versus 0.8333); the test set contains only 41 delayed parcels, so a few additional misses materially change the estimate.

The chosen model configuration is recorded in `outputs/part_c_final_config.csv`. The threshold table records every required operating point, and the test set is evaluated only after feature selection, tuning, configuration choice, and threshold selection are complete.

## Operations recommendation

### Hubs needing escalation

The three K-Means segments are named by their observed hub-level delay rates. The **Escalate** segment contains nine hubs and has average delay rate **0.4600 (46.00%)**, mean delivery duration **64.6504 hours**, mean distance **470.4757 km**, and mean stops **84.3444**. Escalation hubs and their individual historical delay rates from `outputs/hub_profile.csv` are:

| Hub | City | Observed delay rate |
|---|---|---:|
| HUB13 | Nagpur | 0.4600 |
| HUB15 | Kochi | 0.3600 |
| HUB17 | Patna | 0.4600 |
| HUB18 | Ranchi | 0.3800 |
| HUB19 | Guwahati | 0.6200 |
| HUB20 | Raipur | 0.4800 |
| HUB21 | Bhubaneswar | 0.4000 |
| HUB23 | Siliguri | 0.4400 |
| HUB24 | Agartala | 0.5400 |

Hub tier and observed segment disagree for four hubs (`outputs/tier_vs_segment_mismatch.csv`): **HUB07 Kolkata** is Tier 1 but Watch; **HUB13 Nagpur** and **HUB15 Kochi** are Tier 2 but Escalate; and **HUB22 Dehradun** is Tier 3 but Watch. Tier should be treated as an administrative or capacity label, not as a substitute for observed operating performance; review the four exceptions before choosing a playbook.

The chosen alert threshold is **0.5**. At that operating point the held-out test precision/recall imply roughly 6.9 of every 10 flagged parcels are actually delayed and roughly 7.6 of every 10 delayed parcels are caught. In the 48-row incoming batch, **8 parcels are flagged**; **6** need a hub-manager escalation and **2** need a proactive customer call. The action list is in `outputs/new_shipment_actions.csv`.

We keep **K = 3** because the operating process has exactly three playbooks: Standard, Watch, and Escalate. The across-to-within separation ratio rises from **2.8940** at K = 2 to **5.3928** at K = 3, so three clusters separate the hubs much more clearly than two. Although the ratios rise further to **6.3047** and **6.8866** for K = 4 and K = 5, those solutions contain clusters smaller than six hubs (sizes **8-7-5-4** and **8-7-4-3-2**), too small to carry a stable, separate operational playbook.

## Production plan

The current repository is an offline proof of concept. Before any real operational deployment, it would need real, permissioned data, monitoring infrastructure, operational ownership, security review, and a controlled rollout.

### Production-readiness characteristics mapped to this repository

| Characteristic | Concrete evidence or next step |
|---|---|
| Accuracy | `outputs/part_b_metrics.csv` and `outputs/part_c_final_test.csv` report holdout metrics; threshold selection explicitly prioritizes recall. |
| Reliability | `clean_shipments` handles duplicates, missing values, scanner-fault weight sentinels, and missing-payment placeholders; hub joins use `validate="many_to_one"`. |
| Reproducibility | `generate_data.py`, fixed seeds, pinned `requirements.txt`, persisted CSV outputs, and an ordered run sequence reproduce the workflow. |
| Performance | Batch inference vectorizes feature preparation and probability scoring; the 48-parcel batch runs locally without paid services. Benchmark with realistic production volume before rollout. |
| Maintainability | The six stages are separated into scripts, and shared transformations live in `src/shipment_prep.py`. |
| Consistency | Training and inference call the same `clean_shipments` and `build_features` functions; `models/feature_order.csv` pins the feature order and `models/impute_values.csv` stores fill medians. |
| Monitorability | A production extension should log scored volume, flag rate, eventual delay outcomes, calibration, and input-feature drift by week and hub. |

### Proposed monitoring triggers

These are proposed initial operational guardrails, not thresholds learned or validated by this synthetic dataset:

1. **Actual delayed share:** review the operating process when the completed-shipment delayed rate differs by more than **5 percentage points** from the comparable baseline for **two consecutive weeks**. Compare sale periods with equivalent sale periods.
2. **Flagged share:** investigate if the weekly share flagged moves by more than **10 percentage points** from its trailing eight-week baseline, or falls outside a provisional **5%–30%** band. Calibrate this band using real operating capacity before use.
3. **Matured-label recall:** review the model and threshold if recall is below **0.75** over the latest **100 labelled shipments**; if a week contains too few completed outcomes, pool multiple weeks.
4. **Input drift:** investigate if population stability index (PSI) exceeds **0.20** for a core numeric feature such as distance or stops, or if service-type/hub mix changes materially.

### Retraining and seasonal handling

Review performance weekly and retrain on a **monthly** cadence after shipment outcomes have matured, or sooner after a sustained trigger. Re-run validation, threshold selection, and a time-based holdout evaluation before replacing the deployed artifact. During the **15–28 September sale window** (`sale_event_flag`), compare metrics against equivalent sale windows or other comparable promotions—not ordinary weeks—because demand mix and operational load differ. Data drift here may appear as changes in distance, stops, service-type mix, hub workload, rain exposure, sale-period share, or the relationship between these inputs and delivery outcomes.

## Limitations

1. **Synthetic data:** the results measure behaviour in the supplied generator, not real Delhivery operations; no deployment or business-impact claim is made.
2. **Small test sample:** the test set contains only **41 delayed parcels**, so precision and recall have meaningful sampling uncertainty.
3. **Single split and threshold:** the selected configuration and 0.5 threshold use one pinned train/validation split. Real deployment needs repeated or time-based validation and threshold review.
4. **Hub profile scope:** each hub is summarized from 50 synthetic historical shipments. Real hub seasonality and changing capacity are not captured well by this compact profile.
5. **Limited production surface:** this repository implements local batch scoring, not an authenticated API, live monitoring dashboard, automated retraining service, or integration with dispatch/customer-contact systems.
6. **Action costs are simplified:** the threshold rule encodes a recall floor but does not model the real cost of an unnecessary call versus a missed delay; operations should set the final policy using measured costs and staffing capacity.
